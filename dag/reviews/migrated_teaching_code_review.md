# Relocated teaching code: scope and reuse

All **18 original files** from the WAS, EIS and PCIV teaching-code packages have complete source readings. Their relocated bodies were read directly; the three original README versions were also read from the migration recovery archive. Source hashes distinguish the authorized test-path edits from unchanged code.

These are small simulations and teaching components. They should not count as 32 verified workflows merely because their classes and tests carry numbered level labels.

The most consequential result is in PCIV: retro-inheritance **assigns better correctness and latency without evaluation**, even when an empty reflection leaves the genotype unchanged. Such values are synthetic dynamics and cannot be used to measure model improvement. The forge also permits task-changing edits without protected-core checks.

Other bounded countercontrols found:

- WAS profile splicing preserves the compared input/output profiles, but its operation records do not satisfy the tested unit/associativity equalities. Tree typing is unchecked.
- The WAS contraction predicate accepts a jump from zero to 100 and does not enforce its declared contraction factor.
- The EIS “external admission” filter uses only its innate byte/phrase check. It does not consult its stored thymus or an external decision.
- PCIV's standalone frontier selector retains dominated duplicate-ID entries. Taint is a snapshot; later descendants need rescanning. Island capacity and quarantine are not enforced by migration.
- PCIV's hash-chain check accepts a truncated prefix while its retained head still names the removed tail. Ordinary payload alteration is detected.
- Teaching receipt dictionaries remain mutable; a stored digest alone does not make them authenticated or append-only.

There is useful positive evidence within scope. The PCIV graph methods passed **512 ancestor/descendant comparisons over all 64 forward-edge DAGs on four ordered vertices**. Its two-node inverse rank agrees with an exact stationary equation under uniform dangling redistribution. Colour rejection, a distinct-ID dominance control, finite fixture evaluation and ordinary hash-tamper detection are also concrete mechanisms.

The reports retain these code packages as teaching references. A benchmark adaptation needs actual task preservation, external evaluation and usage accounting, explicit custody checks and a named algorithm/policy. No provider, native build, original-source edit or private benchmark access occurred.

Exact findings and controls are in `additional_migrated_operad_teaching.json` and `additional_migrated_eis_pciv_teaching.json`. Prior migration tests are not counted as fresh executions.
