PFP V: A Practitioner's Guide to Checked Proposals

2026-10-02 · Version 0.1.0 · Practitioner guide · Author-review revision

Purpose and reader outcome
This guide takes one small inconsistent graph through a complete session: declare the instance,
propose a change, interpret a refusal, admit a repair, check the result, and restore an earlier state.
It is a practitioner companion to the Proposal Fidelity Protocol (PFP) research series and its legacy
Symbol Game implementations. It adds no new theorem or measured model-performance result.
A proposal is a candidate supplied by a person, script, or model. A host is the program that
applies the declared checks. A receipt records what a particular execution checked and returned.
These roles matter because a plausible proposal can be wrong, while a successful check can establish
less than its surrounding prose suggests.
The first session uses a scripted proposer. No model account, API key, or live conversation is needed.
You should finish able to explain both an accepted move and the limits of its acceptance.
1. Declare the instance before solving it
Suppose three events have proposed offsets on one linear time axis:
• Event b is one unit after event a.
• Event c is one unit after event b.
• Event a is one unit after event c.
This is a mathematical offset example. There is no wraparound clock or recurring-day convention.
Declare those conventions differently and you have a different problem.
Represent the events by vertices a, b, c and the statements by directed edges. The ordered claim
vector is
𝑐 = (𝑐𝑎𝑏, 𝑐𝑏𝑐, 𝑐𝑐𝑎) = (1, 1, 1).
A vertex potential assigns a number 𝑓𝑎, 𝑓𝑏, 𝑓𝑐 to the vertices. Its edge differences are
𝑑𝑓 = (𝑓 𝑏 − 𝑓𝑎, 𝑓 𝑐 − 𝑓𝑏, 𝑓 𝑎 − 𝑓𝑐).
The differences always sum to zero: each vertex value appears once with each sign. The supplied
claims sum to three. Consequently, no potential satisfies all three unchanged claims.
For the common series example, declare edge weights 𝑤 = (1, 2, 3) . A weight is the penalty for
leaving one unit of discrepancy on that edge. It is a modeling choice, not evidence that one event
is more truthful. The complete instance therefore includes the vertices, directed edges, edge order,
exact claims, weights, and permitted changes.

2. Separate a residual from a changed claim
For a chosen potential, the residual is 𝑟 = 𝑐 − 𝑑𝑓 . Its weighted discrepancy is
𝐷𝑐(𝑓) = |𝑟 𝑎𝑏| + 2|𝑟𝑏𝑐| + 3|𝑟𝑐𝑎|.
The quotient minimum is the smallest such discrepancy over all potentials:
Φ𝑤(𝑐) = min
𝑓
𝐷𝑐(𝑓).
The notation distinguishes the score at one chosen potential from the best possible score for un-
changed claims. A poor potential can make 𝐷𝑐(𝑓) larger without changing Φ𝑤(𝑐).
Take 𝑓 = (0, −2, −1) . Then 𝑑𝑓 = (−2, 1, 1) , so 𝑟 = (3, 0, 0) and 𝐷𝑐(𝑓) = 3 . For every potential, the
residual still sums to three. Because all weights are at least one,
𝐷𝑐(𝑓) ≥ |𝑟 𝑎𝑏| + |𝑟𝑏𝑐| + |𝑟𝑐𝑎| ≥ |𝑟 𝑎𝑏 + 𝑟𝑏𝑐 + 𝑟𝑐𝑎| = 3.
The displayed potential attains this lower bound. This short argument establishes the minimum for
this instance without requiring trust in a solver.
Two operations now have different meanings. Choosing that potential concentrates the original
discrepancy on one edge; the original cycle sum remains three. Replacing the claims themselves
by 𝑐′ = (−2, 1, 1) produces a new consistent instance: 𝑐′ = 𝑑𝑓 and Φ𝑤(𝑐′) = 0 . The governor
demonstration performs this second operation through step_cut(proposed_claims=...). Acceptance
says the changed claims satisfy the declared graph check. It does not establish that the changed
event statement is factually correct.
3. Choose the executable path
The supported tutorial in this package is code/quickstart.py. Its Python wrapper sends exact
graph inputs to the pinned Rust calculator. The repository also contains a separate historical root
quickstart.py; the commands here intentionally name the package file.
Use Python 3.10 or newer. The package is self-contained: it carries copies of the two modules it
needs from the repository, the native graph adapter code/native_functional.py and the Paper 004
graph governor code/l1_symbol_game_governor.py . Each copy begins with a header that names
its source path and commit, gives the SHA-256 of the source bytes, and lists the local changes. Apart
from its header, the adapter differs from the source baseline only in import order. The governor copy
is later than the baseline, and this package patches it in two places: it uses the native calculator
only when one is configured and then lets every native refusal propagate, computing the minimum
by exact Python enumeration otherwise (Section 4), and it refuses a CUT that omits a declared
edge (Section 5). Inside a checkout of the source repository, code/tests/test_vendored_sources.py
compares both copies with the recorded Git objects; elsewhere that comparison skips and says why.
The native calculator itself is not part of this package. Build the solve_graph_phi1 executable from
the reviewed source with the repository’s Rust workspace, on any platform:
cargo build --locked -j 1 --manifest-path omega_engine/crates_rs/Cargo.toml -p
omega_functional --bin solve_graph_phi1

Offline arithmetic when the native calculator is unavailable
You can still understand and check the finite argument. Run this ordinary Python snippet, or
evaluate it by hand:
from fractions import Fraction as Q
claims = (Q(1), Q(1), Q(1))
potential = (Q(0), Q(-2), Q(-1))
edge_differences = (
potential[1] - potential[0],
potential[2] - potential[1],
potential[0] - potential[2],
)
residual = tuple(c - d for c, d in zip (claims, edge_differences))
assert edge_differences == (Q(-2), Q(1), Q(1))
assert residual == (Q(3), Q(0), Q(0))
assert sum (edge_differences) == 0
assert sum (residual) == 3
This is an arithmetic worksheet. It neither calls the native adapter nor emits a canonical functional
receipt. Its lower-bound explanation is the argument in Section 2. The package test code/tests/t
est_offline_worksheet.py runs this block as printed. Record a native run as unavailable until the
required calculator can execute.
4. Follow the complete session
play_demo.py imports the package’s copy of the graph governor. Its graph uses weights (1,2,2), a
legacy variant of the common series example’s (1,2,3). Both have the same unique cheapest edge,
minimum three, and displayed repair. The all-zero potential costs five in the script and six in the
common example; those are scores of one potential, not the quotient minima.

When OMEGA_FUNCTIONAL_GRAPH_BIN is set, the governor asks that native calculator,
and any refusal or error it returns stops the step; no Python value is substituted. When it is
not set, the governor computes the quotient minimum by exact Python enumeration of spanning-
tree potentials. Without a configured calculator the session therefore still runs, but its printed
values are Python enumeration results, not native results. Edge weights must be exact integers
or fractions on both paths; floating-point and Boolean weights are refused. The package test

The bad proposal sums to five. Its optimum is five by the same lower-bound argument, with all
discrepancy placeable on the weight-one edge. The host refuses an increase from three to five. A
refused proposal does not replace the active claims.
The good proposal changes the cheapest edge from one to minus two. It supplies a consistent
replacement. The demonstration saves a snapshot before either CUT and uses that snapshot’s
actual identifier when retracting. Do not guess a snapshot identifier from a printed step count.
ASSERT installs the starting problem; it is not a claim that every initialization step decreases
discrepancy. The governor’s CUT checks permit non-increase. A tied score can therefore return
IdempotentStationary. Strict progress and finite termination of an arbitrary search require addi-
tional conditions; repeating an admitted stationary move is not a solution strategy.

The native transport can also fail before a governor verdict exists. Keep the transport exception
and native response, if any, with the run record. A missing calculation is not a zero discrepancy.
Use integers and Fraction inputs for mathematical values. The tutorial rejects floats and Boolean
values at its mathematical input boundary. In particular, Python’s treatment of True as an integer-
like value must not turn it into a declared numerical witness.
6. Reproduce a result and inspect its custody
A useful reproduction record names the source revision, exact input, command, Python version,
native executable digest, exit status, and output. If files change during a run, identify which
version each observation belongs to. Preserve refused cases alongside admitted ones: they show
whether the gate discriminates.
Run the package checks from this package’s directory, one test file per command:
python -m pytest code/tests/test_offline_worksheet.py -q
python -m pytest code/tests/test_play_demo.py -q
python -m pytest code/tests/test_quickstart_native.py -q
The fixture consumes only explicitly supplied OMEGA_FUNCTIONAL_GRAPH_BIN and
OMEGA_FUNCTIONAL_GRAPH_SHA256. It discovers no checkout, builds no program,
and creates no pin. Missing configuration skips, with that reason, every test that requests native
execution. A malformed digest, unreadable configured executable, or digest mismatch fails those
tests with an explicit message. The worksheet, the offline session, the refusal, exact-input, parser,
and scaffold checks, and the vendored-source header checks still run without native configuration.
The commands are replay instructions, not a reported fresh pass.
The existing execution receipt , cross-domain receipt , and series completion receipt are historical
artifacts until their source and executable bindings are reconciled with a new run. A SHA-256 digest
can bind bytes. It does not establish their truth, authenticate an unsigned producer, or supply a
missing experiment. A restricted sorted-JSON encoding also needs its own stated contract; it should
not be called full RFC 8785 conformance without checking that specification.

7. Map a new problem carefully
Before adapting the example, write down what a vertex means, what an edge value measures,
why the edge-difference relation is appropriate, and which changes are allowed. Supply units and
direction conventions. Decide whether changing a claim is an acceptable correction or would replace
an observation you must preserve.
For example, measured offsets might need an uncertainty model rather than unrestricted replace-
ment. A dependency relation might be Boolean rather than an additive quantity. Encoding either
as this graph is a modeling step that requires justification. Renaming vertices to “currency,” “per-
mission,” or “quantum state” does not supply that justification.
The package’s four labeled graph scenarios illustrate repeated use of the finite interface. Their
labels do not establish market equilibrium, authorization security, or a quantum no-go theorem.
The governed scripts make no LLM calls, so hypothetical unconstrained-chat costs in older records
are not a measured comparison.
For model integration, keep the proposer behind the same boundary: parse the proposed fields,
check the declared carrier and operations, recompute the relevant property, and save the actual
response. Consult the streaming harness as an implementation example; reviewing its adapter does
not establish a live provider run. The harness accepts integers and exact rational strings as claim
values and refuses a JSON float or Boolean before any scoring, since Fraction(0.1) is the binary
expansion of the float rather than one tenth (code/tests/test_harness_exact_inputs.py).
8. Connections and next reading
The familiar idea of an untrusted producer supplying evidence to a checker appears in Necula’s
proof-carrying code . That work concerns proofs of a declared code-safety policy. It supplies context
for separating proposal production and evidence checking; this tutorial does not claim its graph
receipt is such a proof.
The minimization and lower-bound reasoning connect to linear-programming duality; see Boyd and
Vandenberghe, Convex Optimization, Chapter 5. The series’ graph mathematics paper develops the
finite theory; Paper 004 explains native verification and evidence custody. The curriculum-design
guide turns examples into lessons, and the review protocol explains how to audit a claimed result.
This guide supports a finite, inspectable proposal–check workflow. Its practical success criterion
is that the reader can state the original instance, explain the failed proposal, distinguish residual
concentration from claim replacement, and identify exactly what a fresh receipt records. General
semantic correctness and model quality need their own evidence.
9. Limitations
The guide works one three-edge instance by hand and describes one scripted session. The pack-
age tests check the session table on the governor’s exact Python enumeration path. For this
revision the native-requesting tests were also run against a solve_graph_phi1 executable built
on Windows (x86_64-pc-windows-msvc, Rust 1.98.0) with cargo build --locked -j 1 from the
omega_functional crate, whose source is unchanged since the code baseline; with that executable
and its SHA-256 (2b0379557993246cacb1ed8964f9f096964019ecc1c2fb781e6b18f2ca6c8a65)
pinned, all 75 package tests passed and none was skipped. The dated review receipt records that
run. The executable is not part of the deposit, so another reader must build and pin their own.
