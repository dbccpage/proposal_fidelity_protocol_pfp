### 3.2 Exhaustive Repository Audit of `negative_fixture` and `positive_fixture` Readers
Scanning all tracked Python and Rust production modules in `pfp/`, `eis/`, `ops/`, `operads/`, and `code/rust/` shows that `negative_fixture` and `positive_fixture` appear exclusively in three non-matching, non-repair-synthesizing roles:
1. **Record Construction and Persistence**:
   Seeders, harvesters, and distiller helpers populate string fields when writing candidate entries—for example, `ops/adversary/use_cases/cemetery_regression.py::distill_pharmacy_antibody` (`lines 365-366`) writes `"negative_fixture": ""` and `"positive_fixture": ""`, while 49 of the 61 entries in `pharmacy_catalog_52cb5457f6c4.json` store `# Triggering defect: <target_pattern>\n` and `# Repaired exact state\n`.
2. **Canonical Rule-Content Digesting (Excluded from Search Outputs)**:
   `eis/domain/pharmacy_search.py:15-29` (`RULE_CONTENT_KEYS`) and `code/rust/core_epistemic_immune_system/src/pharmacy_search.rs:35-46,93-110` (`RULE_KEYS` in `rule_digest`) include `negative_fixture` and `positive_fixture` solely to compute `rule_sha256`. Both `PharmacyMatch` (`pharmacy_search.py:43-50`) and `candidate(...)` (`pharmacy_search.rs:253-257`) omit `negative_fixture` and `positive_fixture` from returned match payloads:
   ```rust
   json!({
       "antibody_id": id, "rule_digest": current, "guidance_text": guidance,
       "target_pattern": record["target_pattern"], "scope": scope,
       "admission_reference": admission,
   })
   ```
3. **Admission Digest Non-Identity and Caller-Supplied Booleans**:
   `eis/domain/external_admission.py:134-155` checks `positive_fixture_digest != negative_fixture_digest` on `ExternalAdmissionRequestV1`, and `FixtureValidationEngineV1.validate_binding` (`lines 423-444`) evaluates caller-passed boolean outcomes `mock_detector_matches: list[bool]` (`not mock_detector_matches[0]` / `mock_detector_matches[1]`). Neither module evaluates incoming proposals against fixture strings or derives a repair from `positive_fixture`.

### 3.3 Nearest Proposal-Screening Consumers (`target_pattern` Substring vs. Regex)
Direct inspection of all proposal/candidate screening paths in the repository confirms how antibody records are consumed at runtime:
1. **Active Python Substring Consumer (`ops/adversary/use_cases/cemetery_regression.py`)**:
   - `_pattern_of(antibody)` (`lines 36-48`) reads only `target_pattern` (or `failure_pattern`) and `failure_class`; AST inspection confirms zero references to `negative_fixture` or `positive_fixture` anywhere in `_pattern_of`, `_validate_catalog`, `_screen_antibodies`, or `screen_known_regressions`.
   - `_screen_antibodies(candidate, text, antibodies)` (`lines 214-226`) tests literal Python substring membership:
     ```python
     for antibody in antibodies:
         for pattern in _pattern_of(antibody):
             if pattern in text:
                 return _refuse(
                     "REGRESSION_AGAINST_ANTIBODY_REFUSED",
                     f"Candidate '{candidate.candidate_id}' matches admitted antibody '{_antibody_id(antibody)}' (pattern: {pattern}).",
                 )
     ```
   - Module docstring lines 3-4 explicitly record this substring semantics (`"it does not treat antibody text as a regular expression"`), and the function returns a refusal (`Err(Refusal(...))`) without reading `positive_fixture` or synthesizing any repair.
2. **Compiled-Regex Guard Consumers (`oeeis_immune.py` and `pharmacy_search.rs`)**:
   `OeeisImmuneAdapter.validate_candidate_against_yaml_specs` (`ops/adversary/infrastructure/estates/oeeis_immune.py:404-421`) and `attach_candidate_hits` (`code/rust/core_epistemic_immune_system/src/pharmacy_search.rs:353-366`) compile only `target_pattern` (`compile_safe_pattern(spec["target_pattern"])` and `regex::Regex::new(rule["target_pattern"])`), read neither `negative_fixture` nor `positive_fixture`, and emit refusal/hit diagnostics rather than positive-fixture repairs.
