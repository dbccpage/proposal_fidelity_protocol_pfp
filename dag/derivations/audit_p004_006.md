# AUDIT-P004-006: Host Bounds and Timeout Validation

## 1. Claim Statement

Input byte ceilings and carrier preallocation bounds are enforced during host intake; the execution timeout parameter is validated metadata constrained to a declared numerical interval ($1 \le \text{timeout\_ms} \le 300{,}000$) with no internal watchdog timer or cancellation thread.

## 2. Context & Hypotheses

- **Native Host Implementation**:
  - Implemented in `code/rust/pfp/src/main.rs`, `code/rust/pfp/src/protocol.rs`, and `code/rust/pfp/src/host.rs` (with `code/rust/pfp/src/host/intake.rs`).
- **Resource Constraints**:
  - `MAX_HOST_REQUEST_BYTES = 1_048_576` (1 MiB) in `protocol.rs` and `host.rs`.
  - `MAX_CARRIER_DIMENSION = 4096` in `protocol.rs`.
  - `MAX_DENSE_MATRIX_CELLS = 1_048_576` in `protocol.rs`.
  - `MAX_TIMEOUT_MS = 300_000` (5 minutes) in `host.rs`.
- **Bounded Intake Model**:
  - Process intake consumes a bounded prefix from standard input and rejects oversized payloads before downstream JSON parsing or solver execution.

## 3. Derivation / Evidence

### 3.1 Input Byte Limits at Process and Module Boundaries
In `code/rust/pfp/src/main.rs:38-42`, the stream reader consumes only a bounded slice:
```rust
fn read_request_prefix(reader: impl Read, limit: usize) -> io::Result<Vec<u8>> {
    let mut input = Vec::new();
    reader.take((limit + 1) as u64).read_to_end(&mut input)?;
    Ok(input)
}
```
If `input.len() > limit`, the process refuses with `CLASSIFY_BOARD_REQUEST_TOO_LARGE` or `RUNTIME_REQUEST_TOO_LARGE` without reading further bytes or constructing unconstrained heap structures.

At the host module boundary in `code/rust/pfp/src/host.rs:73-85`:
```rust
pub fn evaluate_request_bytes(bytes: &[u8]) -> HostOutcomeV1 {
    if bytes.len() > MAX_HOST_REQUEST_BYTES {
        return base_refusal(
            None,
            None,
            "INTAKE",
            "REQUEST_TOO_LARGE",
            format!(
                "request has {} bytes; maximum is {MAX_HOST_REQUEST_BYTES}",
                bytes.len()
            ),
        );
    }
    match strict_json::<HostRequestV1>(bytes) { ... }
}
```
Payloads exceeding `MAX_HOST_REQUEST_BYTES = 1_048_576` return a typed refusal at stage `"INTAKE"` with code `"REQUEST_TOO_LARGE"` before JSON deserialization.

### 3.2 Preallocation Bounds and Matrix Fences
In `code/rust/pfp/src/protocol.rs:47-48`, the host defines static resource limits:
```rust
pub(crate) const MAX_CARRIER_DIMENSION: usize = 4096;
pub(crate) const MAX_DENSE_MATRIX_CELLS: usize = 1_048_576;
```
During carrier intake in `protocol.rs:535-560`, `validate_carrier_resource_fence` checks carrier complex dimensions:
1. $0 < |V| \le 4096$.
2. $0 < |E| \le 4096$.
3. $|F| \le 4096$.
4. $|V| + |F| \le 4096$.
5. Matrix cell bounds: dense matrix construction calculates `cells = rows * cols`; if `cells > MAX_DENSE_MATRIX_CELLS`, intake fails with an explicit error detailing cell count and the ceiling.

In `code/rust/pfp/src/host/intake.rs:108-137`, `validate_budgets_and_carrier` verifies that declared request budgets respect these fences:
```rust
let budgets_ok = [
    b.max_request_bytes == MAX_HOST_REQUEST_BYTES,
    b.max_candidates == 1,
    (2..=64).contains(&b.max_prime_writes),
    (1..=MAX_CARRIER_DIMENSION).contains(&b.max_edges),
    (1..=MAX_CARRIER_DIMENSION).contains(&b.max_vertices_plus_faces),
    (1..=MAX_TIMEOUT_MS).contains(&b.timeout_ms),
]
.into_iter()
.all(|ok| ok);
```
If edge or vertex-face counts exceed the fences, the host refuses with `"RESOURCE_FENCE_EXCEEDED"`.

### 3.3 Timeout Parameter as Validated Metadata Without Internal Watchdog
In `code/rust/pfp/src/host/intake.rs:116`, the timeout value is bounded:
```rust
(1..=MAX_TIMEOUT_MS).contains(&b.timeout_ms)
```
where `MAX_TIMEOUT_MS = 300_000` (5 minutes). If `b.timeout_ms == 0` or `b.timeout_ms > 300_000`, the request is refused with `"RESOURCE_PROFILE_INVALID"`.

Source code inspection confirms:
1. Zero thread spawns, timers (`std::time::Instant` or timer channels), or signal handlers are established to terminate long-running solver loops based on `timeout_ms`.
2. The `timeout_ms` integer is recorded in the outcome and request structures as validated metadata.
3. Enforcement of wall-clock process duration is left to external process supervisors (such as parent orchestrators or container runtimes) rather than an in-process watchdog thread.

## 4. Limits and Non-Claims

1. **Absence of Host Watchdog**: Validation of `timeout_ms` bounds the declared metadata parameter; it does not terminate a runaway computation from within the native process.
2. **Fence Scope**: Resource fences bound carrier dimension to 4096 and matrix cells to 1,048,576; behavior on unvalidated configurations outside this fence is refused rather than computed.
3. **In-Process Memory Bounds**: Byte ceilings limit input buffer allocation; system-level memory usage depends on the host operating system allocator.

## 5. Claim Hygiene Summary

1. **What it supports**: Confirms that `main.rs`, `protocol.rs`, and `host.rs` enforce input byte ceilings (1 MiB), carrier dimension fences (4096), and matrix cell preallocation bounds (1,048,576), and validate `timeout_ms` within $[1, 300000]$ without spawning an internal watchdog timer.
2. **What it does not support**: Does not support claims that the native executable internally cancels executing solvers upon timeout expiration.
3. **Narrowest defensible claim**: Host input buffers and carrier preallocations are bounded by static ceilings, and the timeout field is validated configuration metadata with no internal cancellation watchdog.
4. **Next test needed**: Execution of an artificial non-terminating loop to confirm that native process termination relies on external process signals.
