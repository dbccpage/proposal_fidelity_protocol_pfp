## 1. Claim Statement

The default host, runtime dispatcher, and foundation library are distinct interfaces with segregated entry points, payload byte limits, and dispatch logic.

## 2. Context & Hypotheses

- **Rust Native Codebase**:
  - Located in `code/rust/pfp/src/`.
  - Modules under audit:
    1. CLI entry point and top-level routing in `main.rs`.
    2. Restricted prime host library in `lib.rs` and `host.rs`.
    3. Multi-action runtime invocation dispatcher in `invoke.rs`.
    4. Pure additive mathematical foundation library in `foundation.rs`.
- **Architectural Seams**:
  - Tripartite interface boundary articulated in Paper 004 Section 3: "Three interfaces, three different capabilities."
  - Contracts verified in `code/rust/tests/pfp/host_contract.rs`, `invoke_contract.rs`, and `foundation_contract.rs`.

## 3. Derivation / Evidence

### 3.1 CLI Entry Point and Argument Branching
In `code/rust/pfp/src/main.rs`, the executable partitions operations at the CLI argument boundary:
1. `dispatch_stdin_operation(operation, input, stdout)` routes stdin requests according to the first command-line argument:
   - When `operation == None`: Calls `evaluate_request_bytes(input)` (restricted prime host), returning a serialized `HostOutcomeV1`.
   - When `operation == Some("invoke")`: Calls `invoke_runtime_command(input, &mut stdout)` (runtime dispatcher), which decodes `RuntimeRequestV1` and routes to `dispatch_runtime_request(&req)`.
   - When `operation == Some("--derive-carrier-manifest")` or `Some("classify-board")`: Invokes dedicated administrative utilities.
   - Any unrecognized operation immediately returns an `io::Error` (`"unsupported operation"`).
2. The argument branching ensures that default host execution cannot be invoked through the runtime invocation path, and runtime actions cannot be executed through the default host path.

### 3.2 Payload Byte Limit Segregation
The interfaces enforce distinct input byte ceilings:
1. **Default Host Ceiling**: `MAX_HOST_REQUEST_BYTES = 1_048_576` (1 MiB in `protocol.rs`). Intended for same-carrier candidate evaluation.
2. **Runtime Dispatcher Ceiling**:
   - `MAX_RUNTIME_REQUEST_BYTES = 65_536` (standard runtime envelope).
   - `MAX_DAG_RUNTIME_REQUEST_BYTES = 262_144 + 4096` (260 KiB).
   - `MAX_ADVERSARY_BOUT_RUNTIME_REQUEST_BYTES = 1_048_576` (1 MiB).
   - `MAX_PROMPT_ARTIFACT_RUNTIME_REQUEST_BYTES = 12_582_912` (12 MiB for large artifact evaluation).
3. In `main.rs`, `main()` selects `input_limit` based on whether `operation == Some("invoke")`. Payloads exceeding the configured limit fail fast with `io::ErrorKind::InvalidInput`.

### 3.3 Restricted Prime Host Scope
In `code/rust/pfp/src/lib.rs` and `src/host.rs`:
1. The host maintains atomic, in-process state: `SolveReceipt`, `ReplayedSolve`, `ControlState`, and `StepPermit`.
2. It evaluates a single candidate request against closed solver state, emitting a `HostOutcomeV1` envelope with `AuthorityEffect: None` and unsigned laboratory attestation.
3. The prime host does not import or execute runtime actions (e.g. `EvaluatePatchGates`, `VerifyL1Certificate`, `SimplicialBoundaryDetailed`), maintaining strict separation from cross-language orchestration.

### 3.4 Runtime Dispatcher Scope
In `code/rust/pfp/src/invoke.rs`:
1. The module defines schemas `RUNTIME_REQUEST_SCHEMA` (`core.symbol-game.runtime-request.v1`) and `RUNTIME_OUTCOME_SCHEMA` (`core.symbol-game.runtime-outcome.v1`).
2. It provides multi-action dispatch across more than 20 discrete runtime operations spanning exact algebra, graph homology, and research source ingestion.
3. The dispatcher invokes stateless algorithmic evaluators, operating as a functional FFI seam without maintaining mutable host state machines.

### 3.5 Additive Foundation Scope
In `code/rust/pfp/src/foundation.rs`:
1. The foundation module is purely additive: it defines nullary witnesses (`PrimitiveDifference`), categorical refusal codes (`FoundationErrorCode`), and exact rational structures (`BigRational`).
2. Source inspection confirms that `foundation.rs` contains zero imports of `host.rs` or `invoke.rs`.
3. It does not participate in the host's state machine or the runtime dispatcher's action dispatch, providing uncoupled primitive definitions.

## 4. Limits and Non-Claims

1. **Architectural Interface Boundaries**: This derivation verifies the structural and dispatch separation of the three interfaces within the Rust crate. It does not assert semantic equivalence across distinct programming languages (e.g. Python vs Rust) without separate empirical test witnesses.
2. **No Hardware Security Boundary**: Separation is enforced at the process argument, module, and data-flow levels within a single crate; it does not isolate components into disjoint operating system sandboxes or hardware security modules.
3. **Internal Logic Integrity**: Modular interface isolation prevents cross-interface state contamination; it does not ensure that individual module algorithms are free of domain-specific calculation errors.

## 5. Claim Hygiene Summary

1. **What it supports**: Confirms that `main.rs`, `lib.rs`/`host.rs`, `invoke.rs`, and `foundation.rs` establish three disjoint interfaces with separate entry points, distinct payload ceilings, and independent dispatch logic.
2. **What it does not support**: Does not support claims of formal whole-program verification or cross-runtime identity across disparate compilation targets.
3. **Narrowest defensible claim**: The native Rust codebase partitions the default host, the runtime dispatcher, and the foundation library across distinct source modules with segregated CLI dispatch branches, non-overlapping schemas, and independent data types.
4. **Next test needed**: Stress-testing the CLI entry point with concurrent processes submitting interleaved host and runtime requests to verify memory and descriptor isolation.
