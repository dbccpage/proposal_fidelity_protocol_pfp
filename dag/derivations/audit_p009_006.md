## 3. Derivation / Evidence

### 3.1 Source Inspection of Constructor Disjointness (`Level15AuthorityCalculus.lean`, lines 23–48)
In `namespace MSSN.Level15`:
```lean
inductive StateKind where
  | proposal : StateKind
  | candidateTrace : StateKind
  | quotientWitness : StateKind
  | terminalAuthority : StateKind
  | immutableRefusal : StateKind
  deriving DecidableEq, Repr

def isProposal (k : StateKind) : Prop :=
  k = .proposal ∨ k = .candidateTrace

def isTerminalAuthority (k : StateKind) : Prop :=
  k = .terminalAuthority
```
`theorem1_proposal_non_authority` (lines 39–48) introduces `hp : isProposal k` and `ht : isTerminalAuthority k`, splits `hp` into `h1 : k = .proposal` and `h2 : k = .candidateTrace`, rewrites `ht` to `.proposal = .terminalAuthority` (in branch `inl`) and `.candidateTrace = .terminalAuthority` (in branch `inr`), and closes each goal by `contradiction` using Lean's kernel-generated `StateKind.noConfusion` eliminator (`ctorIdx .proposal = 0 ≠ 3 = ctorIdx .terminalAuthority` and `ctorIdx .candidateTrace = 1 ≠ 3`).

Note also the exact subset structure on the 5-element finite type `StateKind`: although the doc comment at line 22 refers to a state space partitioned into proposal and terminal authority states, `isProposal` holds on 2 constructors (`{.proposal, .candidateTrace}`), `isTerminalAuthority` holds on 1 constructor (`{.terminalAuthority}`), and the remaining 2 constructors (`{.quotientWitness, .immutableRefusal}`) satisfy `¬ isProposal k ∧ ¬ isTerminalAuthority k`. Thus `isProposal` and `isTerminalAuthority` are disjoint subsets rather than an exhaustive two-block cover, so the converse `¬ isTerminalAuthority k → isProposal k` is false (falsified by `k = .quotientWitness` and `k = .immutableRefusal`).

## 4. Limits and Non-Claims

1. **Abstract Tag Inequality Only**: `theorem1_proposal_non_authority` establishes that two nullary constructors of a standalone Lean inductive type do not equal a third constructor of the same type; it models no transition system, parser, cryptographic digest, or external verifier.
2. **Unverified Runtime Correspondence**: Compiling `Level15AuthorityCalculus.lean` provides zero evidence that any Python or Rust gate preserves the separation between candidate proposals and authorized terminal outcomes.
3. **Toolchain Pin vs. Retained Report Header**: In the unpacked archive tree, `lean4/lean-toolchain` pins `leanprover/lean4:v4.35.0` while `lean4/axiom_report.txt` (line 3) records the earlier `leanprover/lean4:v4.34.0` verification run; both `elan`/`lake` `v4.35.0` and `tools/replay_lean_axiom_census.py` execute directly on unmodified CRLF copies of `lean4/` in `tmp_path`, and zero axiom-set differences occur between `v4.34.0` and `v4.35.0` across all 32 theorems.

## 5. Claim Hygiene Summary

1. **What it supports**: Establishes by source inspection and fresh out-of-tree Lean `4.35.0` kernel compilation (`lake build` exit `0`, `Census.lean` / `FullCensus.lean` exit `0`) that `MSSN.Level15.theorem1_proposal_non_authority` derives `isProposal k → ¬ isTerminalAuthority k` with zero axioms via inductive constructor disjointness on `StateKind`.
2. **What it does not support**: Does not support claims that a Python or Rust runtime prevents unauthorized proposal promotion, nor that `isProposal` and `isTerminalAuthority` exhaust all five `StateKind` constructors.
3. **Narrowest defensible claim**: In `Level15AuthorityCalculus.lean` (compiled cleanly under `leanprover/lean4:v4.35.0`), `isProposal` (`{.proposal, .candidateTrace}`) and `isTerminalAuthority` (`{.terminalAuthority}`) are disjoint predicates on the five-constructor inductive `StateKind`, established without axioms by `theorem1_proposal_non_authority`, while runtime state-transition correspondence requires separate implementation evidence.
4. **Next test needed**: Maintain implementation-level falsifier suites (such as input-preservation and digest-bound checker-receipt checks on runtime gates) to test the runtime correspondence obligation that `StateKind` constructor disjointness leaves open.
