## 1. Claim Statement

In `pfp/infrastructure/persistence/cemetery_sink.py`, `CemeterySink._write_file` serializes the full ledger content (line 0 header record and all sequential entries) to a temporary staging path with suffix `.tmp` and replaces the destination target file via `os.replace`.

## 2. Context & Hypotheses

- **Pinned Sink Source**:
  - Implemented in `pfp/infrastructure/persistence/cemetery_sink.py`.
- **Underlying Filesystem Primitives**:
  - Python standard library filesystem operations (`pathlib.Path.write_bytes` and `os.replace`).
- **Target Hypotheses**:
  - `pinned sink source`
- **Open Obligations**:
  - `atomicity depends on the filesystem`

## 3. Derivation / Evidence

### 3.1 Temporary Staging Implementation
Source inspection of `CemeterySink._write_file` reveals:
```python
def _write_file(self) -> None:
    header_record = {
        "authority_effect": "None",
        "entry_count": len(self._entries),
        "genesis_timestamp": self._genesis_timestamp,
        "head_digest": self._tail_digest,
        "record_type": "HEADER",
        "schema": HEADER_SCHEMA,
    }
    all_lines = [_canonical_json_bytes(header_record).decode("utf-8")]
    for entry in self._entries:
        all_lines.append(_canonical_json_bytes(entry.to_dict()).decode("utf-8"))

    content = "\n".join(all_lines) + "\n"

    temp_path = self.file_path.with_suffix(".tmp")
    temp_path.write_bytes(content.encode("utf-8"))
    os.replace(temp_path, self.file_path)
```

1. **Header Record Generation**:
   The header record updates `entry_count` to reflect `len(self._entries)` and `head_digest` to reflect the latest `self._tail_digest`.
2. **Sequential Entry Serialization**:
   Every entry in `self._entries` is serialized to a canonical compact JSON line.
3. **Staging to Temporary File**:
   The combined string is encoded into UTF-8 bytes and written directly to `temp_path = self.file_path.with_suffix(".tmp")`.
4. **Replacement of Target**:
   `os.replace(temp_path, self.file_path)` replaces the target file path with the staged file in a single system call.

### 3.2 Full-File Serialization Semantics
Rather than executing in-place file mutation or partial byte appends, each committed refusal in `record_refusal`:
1. Appends the new `CemeteryEntry` to in-memory state.
2. Updates `self._tail_digest`.
3. Invokes `self._write_file()`, regenerating the full serialized file with updated line 0 count and head digest.

### 3.3 Absence of Dangling Temporary Files
Following execution of `os.replace`, the temporary path is consumed by the filesystem rename operation. No dangling `.tmp` file remains in the ledger directory under normal execution.

## 4. Limits and Non-Claims

1. **Filesystem Atomicity Bounds**: The atomic replacement behavior relies on the operating system and filesystem supporting atomic rename semantics (POSIX `rename` or Win32 `MoveFileEx` with `MOVEFILE_REPLACE_EXISTING`). Certain network or remote filesystems do not support atomic replacement.
2. **Absence of Hardware Durability Call**: `_write_file` does not invoke `os.fsync` or equivalent device flushes; data durability across immediate power interruptions is subject to operating system page cache flush policies.
3. **No Cross-Process Concurrency Locks**: The sink does not acquire inter-process file locks; concurrent unsynchronized process writers to the same ledger file will experience write collisions.

## 5. Claim Hygiene Summary

1. **What it supports**: Confirms that `CemeterySink._write_file` stages serialized JSON-L ledger data to a `.tmp` sibling path and replaces the target file via `os.replace`.
2. **What it does not support**: Does not assert hardware-level power loss durability without explicit fsync, nor thread/process concurrency safety without external locking.
3. **Narrowest defensible claim**: On local filesystem storage, `CemeterySink._write_file` writes full serialized ledger contents to `self.file_path.with_suffix(".tmp")` and replaces `self.file_path` using `os.replace`.
4. **Next test needed**: Evaluating ledger behavior under simulated concurrent writer contention and filesystem failure injection.
