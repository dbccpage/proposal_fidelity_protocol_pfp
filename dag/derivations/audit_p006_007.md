## 1. Claim

Paper 006 Section 4 documents a sorted-key compact JSON encoder in the historical sink. Its implementation does not establish full RFC 8785 conformance. Later encoder observations have separately recorded source identities.

## 2. Historical evidence

The paper identifies implementation baseline `52cb5457f6c485ba548cfd292f6012a941ed22cf`. Its analysis gives two concrete interoperability gaps. Python sorts keys by Unicode code points, whereas RFC 8785 uses UTF-16 code units. The historical helper also left Python's permissive handling of non-finite numbers enabled.

The [first-publication validation receipt](../../atlas/archive/pfp/006_pfp_epistemic_immune_system_and_cemetery_dag_mining/docs/first_publication_validation_2026_10_02.json) records SHA-256 `80dffb00b7f69df406dd968ab891b540fa0a75d83cba33b7a1067a779ad61d24` for the audited `cemetery_sink.py`. The same receipt records a distinct SHA-256, `4ed0e9d9e1d1772a9cbcff917082f387518bfd1a7d53f2f56106faf5228effd6`, for a later source comparison at `2830d21f695e28dbfcf4f07e18a66da948b4a65b`.

## 3. Verification scope

The historical claim rests on the archived source analysis and retained source bindings. The `TestRfc8785ScopeAndFloatRejection` tests in `tests/test_w3_w1_shard_d.py` exercise the present checkout's serializer, including float rejection and tagged encoding. That execution evidence applies to the checked-out revision. A fresh replay of the historical serializer requires its digest-bound source.
