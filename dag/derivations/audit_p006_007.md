## 1. Claim Statement

Canonical serialization in `CemeterySink` defines an internal sorted-key compact JSON profile rather than complete RFC 8785 (JSON Canonicalization Scheme / JCS) compliance. IEEE 754 binary floating-point numbers are rejected with `CanonicalizationError` rather than canonicalized according to RFC 8785 §3.2.2.3.

## 3. Derivation / Evidence

### 3.1 Documented Scope Fence
In `pfp/infrastructure/persistence/cemetery_sink.py`, module-level documentation and function docstrings explicitly declare the non-RFC-8785 scope:
- Module docstring (lines 7–12):
  ```text
  Records are written in a sorted-key compact JSON profile (UTF-8, no
  whitespace, ensure_ascii=False). This profile is not RFC 8785 (JCS): it
  does not implement the JCS number serialization or its UTF-16 key ordering.
  Digested payloads contain no binary floating-point numbers and no NaN or
  infinity; a float supplied to record_refusal is kept exactly as the tagged
  string {"$float_hex": float.hex()}.
  ```
- Function docstring of `_canonical_json_bytes` (lines 90–96):
  ```text
  Encode an object in the sorted-key compact JSON profile, as UTF-8 bytes.
  Keys are sorted, separators carry no whitespace, and non-ASCII text is kept
  as UTF-8. This is not RFC 8785 (JCS). Floats, NaN and the infinities are
  refused with CanonicalizationError rather than written as JSON numbers.
  ```

### 3.2 Float Rejection Implementation
The function `_refuse_floats(obj)` traverses all nested mappings, lists, and tuples:
```python
def _refuse_floats(obj: Any, where: str = "$") -> None:
    if isinstance(obj, float):
        raise CanonicalizationError(
            f"float {obj!r} at {where} is not admitted in a digested cemetery payload"
        )
    if isinstance(obj, Mapping):
        for key, value in obj.items():
            _refuse_floats(value, f"{where}.{key}")
    elif isinstance(obj, (list, tuple)):
        for index, value in enumerate(obj):
            _refuse_floats(value, f"{where}[{index}]")
```
When `_canonical_json_bytes` is invoked with any object tree containing a binary `float` (including finite floats, `float('nan')`, or `float('inf')`), it raises `CanonicalizationError`.

### 3.3 Hex Float Representation in Refusal Records
When a caller supplies a floating-point value to `CemeterySink.record_refusal`, the sanitization helper `_sanitize_for_cemetery` converts the float into an exact hexadecimal tagged dictionary:
```python
if isinstance(obj, float):
    return {FLOAT_TAG: float(obj).hex()}
```
This ensures that the caller's bit-level floating-point value is preserved without emitting a binary float into the digested JSON payload.

### 3.4 Key Sorting and Encoding Differences from RFC 8785
1. **Float Serialization**: RFC 8785 §3.2.2.3 requires standard ECMAScript / IEEE 754 float representation (7.1.12.1 ToString Applied to the Number Type). `CemeterySink` does not implement this representation and instead refuses binary floats.
2. **Key Ordering**: RFC 8785 §3.2.3 specifies sorting object member keys by UTF-16 code units. `_canonical_json_bytes` utilizes Python's `sort_keys=True`, which sorts keys by Unicode code points.

## 4. Limits and Non-Claims

1. **Scope Fence Only**: This derivation records the declared architectural boundary and refusal behavior; it does not claim that the internal profile conforms to RFC 8785.
2. **No General JSON Converter**: The profile is designed specifically for hash-chain digestion within `CemeterySink`; it is not intended as a general-purpose interchange serializer.

## 5. Claim Hygiene Summary

1. **What it supports**: Confirms that `_canonical_json_bytes` rejects IEEE 754 binary floats with `CanonicalizationError` and uses an internal sorted-key profile distinct from RFC 8785.
2. **What it does not support**: Does not support claims of RFC 8785 compliance or broad external JCS canonicalization compatibility.
3. **Narrowest defensible claim**: In `pfp/infrastructure/persistence/cemetery_sink.py`, `_canonical_json_bytes` refuses binary floats with `CanonicalizationError` and implements sorted-key compact JSON serialization with UTF-8 encoding.
4. **Next test needed**: Verifying serialization stability across non-ASCII key strings and boundary numeric representations.
