## 1. Claim Statement

`CemeterySink.record_refusal` persists caller-supplied refusal reasons, prompt parameters, and cochain projections as evidentiary records without independent computation, interpretation, or mathematical verification by the sink.

## 2. Context & Hypotheses

- **Cemetery Sink Implementation**:
  - Implemented in `pfp/infrastructure/persistence/cemetery_sink.py` via `record_refusal`.
- **Target Hypotheses**:
  - `record_refusal source`
- **Open Obligations**:
  - `[]`

## 3. Derivation / Evidence

### 3.1 Method Interface and Parameter Intake
Inspection of `CemeterySink.record_refusal`:
```python
def record_refusal(
    self,
    turn_envelope: Any,
    refusal_reason: str,
    prompt_parameters: Mapping[str, Any] | None = None,
    cochain_projection: Mapping[str, Any] | None = None,
) -> CemeteryEntry:
```
The caller provides:
- `turn_envelope`: metadata regarding the interaction turn.
- `refusal_reason`: reason string identifying why the turn was rejected.
- `prompt_parameters`: optional dictionary of prompt settings.
- `cochain_projection`: optional dictionary containing cochain values or residual components.

### 3.2 Non-Interpreting Storage Path
Inside `record_refusal`:
```python
params = dict(prompt_parameters) if prompt_parameters is not None else {}
projection = dict(cochain_projection) if cochain_projection is not None else {}

envelope_dict = _sanitize_for_cemetery(envelope_dict)
params = _sanitize_for_cemetery(params)
projection = _sanitize_for_cemetery(projection)
```
1. **Pass-Through Custody**: The sink performs shallow copying and type sanitization (converting `Fraction` and `Q` instances to canonical strings, and floats to tagged hex dictionaries).
2. **Zero Mathematical Evaluation**: The sink does not evaluate differential operators, does not check whether $d_1 d_0 = 0$, does not re-solve the carrier complex, and does not determine whether the supplied `refusal_reason` is justified.
3. **Contradictory and Arbitrary Payloads Accepted**: Even if a caller submits an arbitrary string or contradictory cochain coordinates, `record_refusal` accepts and commits the entry into the hash-chain without error.

### 3.3 Cryptographic Binding of Evidentiary Inputs
The entry payload includes all caller-provided fields:
```python
payload = self._entry_payload(
    entry_index=idx,
    timestamp_utc=timestamp_utc,
    turn_envelope=envelope_dict,
    refusal_reason=refusal_reason,
    prompt_parameters=params,
    cochain_projection=projection,
    prev_digest=prev_digest,
)
entry_digest = _sha256_hex(_canonical_json_bytes(payload))
```
Every field supplied by the caller is bound into the SHA-256 entry digest. This establishes custody integrity: once committed, the caller's recorded data cannot be modified without invalidating `entry_digest` and triggering `LedgerIntegrityError` during `verify_integrity()`.

## 4. Limits and Non-Claims

1. **Storage Integrity versus Event Truth**: Committing an entry to `CemeterySink` demonstrates that the record was persisted without tampering; it does not demonstrate that the recorded refusal or cochain projection is factually accurate or mathematically valid.
2. **Caller Trust Responsibility**: The validity of the evidence relies entirely on upstream caller honesty.

## 5. Claim Hygiene Summary

1. **What it supports**: Confirms that `CemeterySink.record_refusal` preserves caller-supplied refusal reason and cochain projection arguments in hash-chained storage without domain validation or independent computation.
2. **What it does not support**: Does not assert that records stored in `CemeterySink` represent objectively verified mathematical facts.
3. **Narrowest defensible claim**: In `pfp/infrastructure/persistence/cemetery_sink.py`, `CemeterySink.record_refusal` commits caller-supplied cochain projections and refusal reasons without evaluating their semantic validity.
4. **Next test needed**: Testing interaction between protocol governors and the sink under simulated malicious caller payloads.
