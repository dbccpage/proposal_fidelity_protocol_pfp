## 1. Claim Statement

For every nonempty declared route (odd, cochain, ...) the baseline verify_route returns `NO_NATIVE_PORT` and certifies no witness.

## 2. Context & Hypotheses

- **Baseline Route Verifier**:
  - The function `verify_route(route_name: str) -> DemoRefusal` is defined in `atlas/archive/pfp/003_pfp_host_admitted_failure_detectors/code/host_engine.py` (lines 159–163).
  - The declared fixtures and routes in `KNOWN_FIXTURES` are:
    1. `"gauge_even_triangle"` -> `"restricted_diagonal_sign_gauge"`
    2. `"gauge_odd_triangle"` -> `"frustrated_parity_gauge"`
    3. `"cochain_exact_cycle"` -> `"discrete_gauge_potential"`
    4. `"meron_two_pairs_survivor"` -> `"meron_cluster_involution"`
    5. `"frustrated_square_diagonal"` -> `"frustrated_diagonal_sign_gauge"`
- **Host Execution Environment**:
  - The host engine evaluates proposed moves sequentially within an atomic batch transaction.
  - A batch requesting verification invokes `verify_route` with the fixture's declared route identifier.

## 3. Derivation / Evidence

### 3.1 Route Refusal Behavior
1. In `host_engine.py` lines 159–163:
   ```python
   def verify_route(route_name: str) -> DemoRefusal:
       if not route_name:
           raise DemoRefusal("UNKNOWN_ROUTE", "")
       return DemoRefusal("NO_NATIVE_PORT", route_name)
   ```
2. For every nonempty string `route_name`, `verify_route` returns a typed refusal instance `DemoRefusal("NO_NATIVE_PORT", route_name)`.
3. For an empty string `route_name == ""`, it raises `DemoRefusal("UNKNOWN_ROUTE", "")`, bounding the input domain.

### 3.2 Non-Certification of Witness
1. During transaction processing in `Demo3HostEngine.execute_batch`:
   - When a move proposal has `move_type == "VERIFY"` (lines 298–315 of `host_engine.py`), the engine queries `verify_route(self.fixture["route"])`.
   - Receiving `refusal = DemoRefusal("NO_NATIVE_PORT", route)` sets `decision = "NO_NATIVE_PORT"`, records `self.route_refusal = refusal`, and flags `rollback = True`.
2. Upon rollback:
   - Semantic state is restored from snapshot (`self.state = snapshot`).
   - The fields `terminal_exit` and `terminal_label` remain `None`.
   - No certificate token is generated or emitted in the resulting receipt.
3. Therefore, across all declared route types (odd parity gauge, cochain potential, meron involution), no witness candidate is certified as accepted.

### 3.3 Historical Test Replay
The behavior reproduces the baseline tests recorded in `paper_claim_ledger.md` row P3-02:
- `test_verify_route_returns_missing_port_without_judging_a_witness`: asserts `refusal.code == "NO_NATIVE_PORT"` and `refusal.detail == "restricted_diagonal_sign_gauge"`.
- `test_odd_and_cochain_routes_use_the_same_refusal`: asserts that all three tested routes (`gauge_odd_triangle`, `cochain_exact_cycle`, `meron_two_pairs_survivor`) yield `host_decision == "NO_NATIVE_PORT"` and `terminal_exit != HostExit.SCOPED_CERTIFICATE`.

## 4. Limits & Non-claims

1. **What it supports**: Confirms that within the audited baseline repository and package host environment, all five declared route fixtures return `NO_NATIVE_PORT` and produce zero certified witnesses.
2. **What it does not support**: Does not indicate that verification logic is ruled out or that formal solutions of the underlying problems do not exist; it documents that native verification ports were unadmitted at this baseline.
3. **Narrowest defensible claim**: For each declared nonempty route in `KNOWN_FIXTURES`, calling `verify_route` returns `DemoRefusal("NO_NATIVE_PORT", route)` and host batch execution commits no witness certificate.
4. **Next test needed**: Testing integration against candidate native solvers when native port adapters are introduced.
