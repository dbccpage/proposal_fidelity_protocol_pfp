# What runs where?

**WF1–WF5 now have standalone automated Python runners.** Install the
`workflows` extra and follow [Install and run](Workflow-Running.md).

| Entry point | Purpose | Model calls |
| --- | --- | --- |
| `python -m pfp.workflows.wf0001` / `pfp-wf1` | Basic P*, typed answer and independent checker. | At most 1 on `run`. |
| `python -m pfp.workflows.wf0002` / `pfp-wf2` | Full slots and emitted operad/DDC collection. | At most 1 on `run`. |
| `python -m pfp.workflows.wf0003` / `pfp-wf3` | Mine, screen, freeze, solve and check. | At most 2 on a fresh run. |
| `python -m pfp.workflows.wf0004` / `pfp-wf4` | One miner, five concurrent solvers, independent global check and LGGR. | At most 6. |
| `python -m pfp.workflows.wf0005` / `pfp-wf5` | Deterministic full seed rewrite plus the six-call structure. | At most 6. |
| `python -m pfp_lab.cli.main` | Local teaching scenarios and receipt verification. | 0. |

`prepare` and `replay` never buy a model response. The fresh-run commands use
Llama 3.3 70B through OpenRouter with a 4,999 micro-USD allowance shared across
all phases. The host uses estimated accounting and fails closed on unknown cost;
it does not promise a vendor-enforced billing ceiling.

## Source and isolation

The five folders are `pfp/workflows/wf0001` through `wf0005`. Each owns its
workflow/version, response bindings and tests. Pure shared components remain
shared; fresh run folders keep mutable state and failures segregated.

The provider, SQLite accounting and LGGR owners already existed under `ops/`.
Package mappings make their logical imports installable without an engine
checkout. The optional native hard-budget library is loaded only when requested;
its absence is a typed refusal rather than an import-time failure.

## Historical evidence stays historical

The October 28 measurements used the older `omega_engine_pfp` integration.
Their versions remain WF1/WF2 0.1.0, WF3 0.3.0, WF4 0.1.0 and WF5 0.1.4.
Migrated versions are WF1/WF2/WF4/WF5 0.2.0 and WF3 0.4.0.
Old manifests and replies were not rewritten to match the new namespace.
New replay requires the implementation identity that prepared that run.

WF5 supports a checked failed-miner continuation that retains settled old costs
and reduces the new allowance. It verifies historical custody without pretending
that an old response was generated by the new implementation.

## Validation scope

Migration validation covers offline regression/negative controls, CLI execution
with scripted accounted providers, concurrency, wheel resources and replay.
No fresh paid model calls were made. [Results and costs](Workflow-Results.md)
keeps the earlier single-seed measurements and their limits.
