## 1. Objective & Purpose

WF29 inverts the standard solver turn: rather than synthesizing an algorithm to solve a problem, the model is tasked with **synthesizing a formal verification checker** for a declared certificate schema.

To verify that the model's synthesized checker is sound and non-vacuous, the host subjects the synthesized code to a rigorous two-pronged evaluation:
1. **Soundness:** It must accept 100% of verified, known-good valid instances (zero false rejections).
2. **Completeness & Rigor:** It must kill 100% of an adversarial, host-generated **mutation suite** (syntax mutants, swapped coordinates, perturbed edge signs, broken duality gaps).

---

## 2. Process Specification

1. **Certificate Schema Declaration:** The host provides a formal specification for a mathematical certificate (e.g. an LP duality certificate or a planar graph 4-coloring).
2. **Checker Synthesis Turn:** The model authors a standalone Python checker function:
   ```python
   def verify_certificate(instance: dict, certificate: dict) -> bool: ...
   ```
3. **Soundness Panel Test:** The host executes the synthesized checker on a panel of pre-computed, known-valid instances.
4. **Hostile Mutation Testing:** The host runs a suite of $M$ programmatic mutations:
   - Perturbing scalar coordinates by $\pm 1$.
   - Swapping primal and dual indices.
   - Deleting boundary constraints.
   - Injecting cycle-inversion errors.
5. **Score Adjudication:** The checker is admitted if and only if it achieves a 100% kill rate on mutants with 0% false rejections on valid cases.

---

## 3. Mathematical Model & Mutation Kill Rate

- **Mutation Kill Rate Metric:**
  Let $\mathcal{M} = \{m_1, \dots, m_M\}$ be the set of perturbed, invalid certificate mutants:
  $$\text{Kill Rate} = \frac{\sum_{j=1}^M \mathbf{1}[\operatorname{checker}(x, m_j) == \text{FAIL}]}{M}$$
- **Soundness Invariant (Zero False Rejections):**
  Let $\mathcal{V} = \{v_1, \dots, v_K\}$ be the panel of valid certificates:
  $$\text{Soundness} = \frac{\sum_{k=1}^K \mathbf{1}[\operatorname{checker}(x, v_k) == \text{PASS}]}{K} == 1.0$$
- **Admission Gate:**
  $$\operatorname{Admit}(\operatorname{checker}) \iff (\text{Soundness} == 1.0) \land (\text{Kill Rate} == 1.0)$$

## 4. Team Structure & Panel Roles

- **Pattern:** `red_team_pair`
- **Normal Path Calls:** 1 synthesis call.
- **Roles:**
  - `coder` (Sonnet, count: $1$): Authors the Python verification checker function.
  - `adversary` (Fable, count: $1$): Generates devious mathematical mutants designed to exploit loose tolerances or missing boundary checks.
  - `host_checker` (None, count: $1$): Deterministic host mutation test harness.
- **Boost Rule:** If a mutant survives the synthesized checker, Opus reviews the surviving mutant code and patches the checker once (limit 1).

---

## 5. Host Verification Protocol

- **Sandbox Execution:** Synthesized checker code executes in a restricted Python environment with resource limits (timeout: 5 seconds, max memory: 256 MiB).
- **Hard Refusal:** Trivial implementations (e.g. `return True` or `return False`) are killed instantly by the combined soundness/mutation panel.

## 6. Claim Hygiene Evaluation

1. **What the Evidence Supports:**
   - Empirical findings in Challenge C060 establish that mutation suites reliably discriminate between robust verification checkers and trivial or vacuous scripts.
2. **What the Evidence Does Not Support:**
   - A 100% kill rate on a finite mutation suite does not formally prove that the synthesized checker is correct against arbitrary unseen bugs.
3. **Narrowest Defensible Claim:**
   - WF29 evaluates synthesized code verifiers against programmatic mutation suites, establishing their empirical ability to accept valid certificates and reject planted mathematical errors.
4. **Next Test Needed:**
