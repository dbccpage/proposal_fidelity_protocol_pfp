---

## 1. Objective & Purpose

WF23 is an automated **harness gate** that audits the integrity and security of benchmark challenge packets before they are distributed to participant models or research teams.

WF23 addresses two critical threats to scientific validity:
1. **Answer Leakage:** Verifying that the expected answer, ground-truth certificates, or trivial shortcuts cannot be reconstructed from the public participant files.
2. **Custody Tampering:** Verifying that the judge executed during evaluation matches the cryptographically signed and sealed reference code bit-for-bit.

---

## 2. Process Specification

1. **Canonical Formatting:** Ingest participant and judge packets, normalizing file encodings, line endings, and JSON key ordering.
2. **Cryptographic Sealing:** Compute the SHA-256 hex digest of every member file and record them in an immutable manifest.
3. **Automated Leakage Audit:**
   - Scan public files for literal occurrences of expected scalar answers, hidden seeds, or salt tokens.
   - Run symbolic and statistical independence tests ensuring the answer cannot be trivially derived from public metadata.
4. **Judge Custody Audit:** Verify that the judge script to be executed in evaluation has an exact SHA-256 match with the registered reference version.
5. **Audit Certification:** Emit a signed `custody_audit_report.json`. If any check fails, the challenge packet is locked and blocked from dispatch.

---

## 3. Mathematical Model & Leakage Invariants

- **Cryptographic File Custody:**
  For each file $f \in \text{Packet}$:
  $$\operatorname{SHA256}(\operatorname{read\_bytes}(f)) == \text{Manifest}[\text{path}(f)]$$
- **Answer-Free Leakage Criterion:**
  Let $P$ denote the public participant bytes and $y^*$ denote the ground-truth solution:
  $$\forall \text{span} \in \operatorname{tokens}(P), \quad \operatorname{similarity}(\text{span}, y^*) < \epsilon_{\text{leak}}$$
  $$\text{MutualInformation}(P; y^*) == 0$$
- **Execution Invariant:**
  The executed judge bytes $B_{\text{exec}}$ must satisfy $H(B_{\text{exec}}) = H_{\text{sealed}}$.

## 4. Team Structure & Panel Roles

- **Pattern:** `red_team_pair`
- **Normal Path Calls:** 0 calls (executed entirely by deterministic host audit scripts).
- **Roles:**
  - `coder` (Sonnet, count: $1$): Runs the audit test suites and verifies cryptographic manifests.
  - `adversary` (Fable, count: $1$): Tries to extract solutions or certificates directly from the participant packet using reconstruction attacks.
  - `host_checker` (None, count: $1$): Deterministic host verifier; evaluates the custody audit report.
- **Boost Rule:** If any leak or hash mismatch is detected, the challenge is immediately blocked; no model dispatch is authorized until the package is remediated and resealed (limit 0).

---

## 5. Host Verification Protocol

- **Audit Tooling:** Executes `pfp.tasks.certified_challenges` audit commands directly against target directories.
- **Pre-Flight Blocking:** Benchmarking scripts check for a valid, passing WF23 audit report; absent a clean report, dispatch fails with `UNAUDITED_CHALLENGE_PACKET`.

## 6. Claim Hygiene Evaluation

1. **What the Evidence Supports:**
   - The repository implements concrete audit scripts that detect substring leaks and hash mismatches in challenge packets.
2. **What the Evidence Does Not Support:**
   - Passing an automated leakage audit does not prove that an advanced model cannot exploit subtle statistical correlations.
3. **Narrowest Defensible Claim:**
   - WF23 provides a deterministic pre-execution gate that confirms that challenge packages match their recorded SHA-256 digests and contain no verbatim answer strings.
