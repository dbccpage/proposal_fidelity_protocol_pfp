---

## 1. Objective & Purpose

WF8 decomposes a complex derivation or computation into a sequence of $k$ distinct, typed stages executed as a relay. Each stage produces an immutable, cryptographically sealed output packet. Downstream stages are strictly isolated: they can only consume the sealed outputs of preceding stages, verified via an unbroken SHA-256 hash chain.

This architecture prevents retroactive goalpost-shifting, hidden intermediate hallucination, and prompt context pollution.

---

## 2. Process Specification

1. **Decomposition & Contract Declaration:** The pipeline declares an explicit decomposition of the task into $k$ sequential stages $(f_1, \dots, f_k)$, specifying the input/output schemas for each stage.
2. **Sequential Relay Execution:**
   - Stage 1 consumes the initial seed prompt and emits `payload_1`.
   - The host verifies `payload_1`, computes its cryptographic seal $h_1$, and freezes the stage artifact.
   - For $i = 2 \dots k$: Stage $i$ receives only $h_{i-1}$ and the frozen output of Stage $i-1$. It emits `payload_i`.
   - The host computes $h_i = H(h_{i-1} \parallel \text{payload}_i)$.
3. **Stage Verification:** Each stage output must satisfy its declared intermediate host checker.
4. **Final Terminal Evaluation:** The terminal answer emitted by Stage $k$ is evaluated against the end-to-end task checker.

---

## 3. Mathematical Model & Cryptographic Hash Chain

- **Pipeline Function Composition:**
  $$F = f_k \circ f_{k-1} \circ \dots \circ f_1$$
  where each stage maps typed domains: $f_i: X_{i-1} \to X_i$.
- **Cryptographic Seal Chain:**
  $$h_0 = \operatorname{SHA256}(\text{seed})$$
  $$h_i = \operatorname{SHA256}(h_{i-1} \mathbin{\Vert} \operatorname{canonical\_json}(\text{payload}_i)) \quad \text{for } i \in \{1, \dots, k\}$$
- **Tamper Evidence:** Modifying any byte in $\text{payload}_m$ ($m < k$) invalidates all subsequent seals $h_m, \dots, h_k$, immediately halting verification.

---

## 4. Team Structure & Panel Roles

- **Pattern:** `relay`
- **Normal Path Calls:** $k$ model calls (one per stage).
- **Roles:**
  - `coder` (Sonnet, count: $k$): Implements each stage transition, reading only sealed upstream outputs.
  - `deep_researcher` (Opus, count: $1$): Specifies the mathematical partitioning and typed stage interface contracts.
  - `host_checker` (None, count: $1$): Verifies per-stage receipts and validates the complete hash chain.
- **Boost Rule:** If a stage receipt fails host verification, that stage may be re-run once using Opus with the typed receipt residual; earlier valid stage seals are preserved (limit 1).

---

## 5. Host Verification Protocol

- **Hash Chain Verification:** The host verifies that $h_i$ matches the SHA-256 digest of $h_{i-1}$ concatenated with the canonical representation of Stage $i$'s output.
- **Stage Receipt Audits:** Intermediate checks verify intermediate invariants (e.g. rank preservation, matrix dimension matching) before authorizing the next stage.
- **Refusal Code:** Any discontinuity in the hash chain emits `SEAL_CHAIN_BROKEN`.

---

## 6. Claim Hygiene Evaluation

1. **What the Evidence Supports:**
   - The repository demonstrates staged packet execution with cryptographic sealing in WF3 (2 stages) and WF4/WF5.
2. **What the Evidence Does Not Support:**
   - Staged decomposition does not guarantee that decomposing a complex problem makes it easier for language models to solve.
3. **Narrowest Defensible Claim:**
   - WF8 provides a multi-stage relay protocol where every intermediate artifact is cryptographically chained and independently verified by host checks.
4. **Next Test Needed:**
   - Implement a 3-stage WF8 pipeline for matrix inversion (LU decomposition $\to$ triangular solves $\to$ product) and measure error propagation across stages.
