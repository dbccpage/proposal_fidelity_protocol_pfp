## 1. Objective & Purpose

WF48 represents the **gold-standard security gate** for benchmarking autonomous solvers and mathematical certifiers. It couples a strict cryptographic commit-reveal protocol with a hostile programmatic mutation suite.

WF48 eliminates two classic forms of benchmark cheating:
1. **Pre-reveal Overfitting:** Participants cannot tune their algorithms to hidden test cases because the solver code hash is permanently committed to the host before the hidden cases are revealed.
2. **Vacuous or Permissive Verification:** A solver cannot pass by emitting loose or degenerate certificates because the host verification checkers are tested against an adversarial mutation suite that must be killed 100%.

## 2. Process Specification

1. **Host Manifest Commitment:** The host publishes public cases and commits the SHA-256 manifest of the sealed judge packet.
2. **Solver Commitment:** The participant or model team freezes their solver implementation and submits a cryptographic commitment:
   $$\text{Commitment} = \operatorname{SHA256}(\text{salt} \mathbin{\Vert} \operatorname{read\_bytes}(\text{solver.py}))$$
3. **Case Revelation:** The host reveals the hidden test cases, which include:
   - Base mathematical problem instances.
   - Relabeling and gauge twin controls (isomorphic problems under relabeled vertices).
   - Poison bait cases (provably unsolvable or contradictory problems).
4. **Evaluation:** The committed solver is executed against the revealed suite.
5. **Hostile Mutation Testing:** In parallel, the host runs the dual verification checkers against a hostile mutation suite of corrupted certificates.
6. **Admission:** The run is certified if and only if the solver passes all valid hidden cases, correctly identifies all poison bait instances, and the host checkers kill 100% of the mutation suite.

## 3. Mathematical Model & Cryptographic Commitments

- **Cryptographic Binding Invariant:**
  $$\text{VerifiedExecution}(S) \implies \operatorname{SHA256}(\text{salt} \mathbin{\Vert} \operatorname{bytes}(S)) == \text{CommittedDigest}$$
- **Gauge Invariance Control:**
  For any relabeling permutation $\pi \in S_{|V|}$:
  $$\operatorname{Solver}(\pi(G)) == \pi(\operatorname{Solver}(G))$$
  A solver that solves $G$ but fails $\pi(G)$ is flagged for superficial memorization.
- **Dual Checker Mutation Invariant:**
  Let $\mathcal{M}$ be the hostile mutation set. Both independent checkers $C_1, C_2$ must reject every mutant:
  $$\forall m \in \mathcal{M}, \quad C_1(m) == \text{FAIL} \land C_2(m) == \text{FAIL}$$

## 4. Team Structure & Panel Roles

- **Pattern:** `red_team_pair`
- **Normal Path Calls:** Budget-capped.
- **Roles:**
  - `coder` (Sonnet, count: $1$): Implements the candidate solver and packages commitment digests.
  - `adversary` (Fable, count: $1$): Synthesizes poison bait cases and programmatic certificate mutations.
  - `host_checker` (None, count: $1$): Deterministic host dual checkers and commit-reveal verifier.
- **Boost Rule:** If any hostile mutant survives both checkers, the verification suite is declared compromised and immediately blocked from certifying results (limit 0).

---

## 5. Host Verification Protocol

- **Dual Independent Checkers:** Verification requires two separate implementations (e.g. one in Python and one in Lean 4 or exact rational arithmetic) to execute against all certificates.
- **Poison Bait Detection:** Failing to refuse a poison bait case is classified as an epistemic bluff and immediately invalidates the run.
